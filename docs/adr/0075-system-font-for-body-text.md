# ADR-0075: 本文を端末の書体で描き、Web フォントを記事の題と見出しの明朝と等幅だけにする

## Status

提案

## Context

和文の書体の読み込みを減らすために、本文の書体と、Web フォントの配り方を決め直す必要がある。

- サイトの基盤の要求は、Lighthouse の Performance が 90 以上で、LCP が 2.5 秒以内であることを求める（Moto G Power、Slow 4G 相当）。
- 2 回目以降の訪問のトップは、Performance が 75、LCP が 5.71 秒で、要求に届かない（simulate、5 回の中央値）。
  - LCP の要素は、庭の和紙に置いたプロフィールの段落で、本文の書体の Noto Sans JP で描く。
  - トップは、Noto Sans JP の分割を 28 ファイル、352 KiB 取得する。
  - 描画を止める CSS は gzip で 179 KiB あり、ほぼ全部が 632 件の `@font-face` である。Noto Sans JP の 400 と 700 が、そのうち 248 件を占める。
- 運営者は、和の感じを残すと決めた。書体は変えてよいとした。
- DADS の書体は Noto Sans JP と Noto Sans Mono で、選んだ理由は可読性と視認性の高いサンセリフであることである。システムの書体を使うことは制限していない。
  - 出典: [DADS のタイポグラフィ](https://design.digital.go.jp/dads/foundations/typography/)
- Zen Old Mincho は、仮名の重心が現代の明朝より低いオールドスタイル明朝である。起筆と終筆に筆意は残るが、活字なので筆文字に当たらない。
  - 出典: [googlefonts/zen-oldmincho](https://github.com/googlefonts/zen-oldmincho)
- 和文の可変の書体は、1 つの分割がウェイトの軸を持つので重い。Noto Serif JP の可変は、1 つの分割が平均 56 KB だった。Zen Old Mincho の静的なウェイトは、1 つの分割が平均 20 KB だった。
- プレイグラウンドの Node の実行環境のパスと、それを埋め込む記事の URL は、`COEP: require-corp` を返す。COEP の下では、CORP を返さないクロスオリジンのリソースがブロックされる。
  - ADR-0034: [cross-origin isolation のヘッダを、プレイグラウンドの Node の実行環境のパスと、それを埋め込む記事の URL にだけ返す](0034-playground-origin-and-embedding.md)
- 書体の CSS（`packages/ui/src/tokens/fonts.css`）は、apps/web、apps/playground、packages/ui の Storybook が読む。
- apps/web のビルドは、記事の題と見出しの Zen Old Mincho の分割を、使う字だけに作り直す（`apps/web/src/lib/subset-fonts.ts`）。apps/playground と Storybook のビルドは、作り直さない。
- Fontsource の Noto Sans JP は、unicode-range の分割と、和文の字をまとめたウェイトごとの 1 ファイル（1.1〜1.2 MiB）を持つ。サイトで使う字だけのファイルは持たない。

## Decision

本文の和文と欧文を、端末の書体で描く。  
Web フォントは、記事の題と見出しの明朝と、等幅だけにする。  
本文の Web フォントの取得をなくすと、トップの Performance が simulate の中央値で 90 に届いたためである。

| 役割             | 書体                                                                                                            | ウェイト  | 配り方                                                         |
| ---------------- | --------------------------------------------------------------------------------------------------------------- | --------- | -------------------------------------------------------------- |
| 本文             | 端末の書体。`"Hiragino Sans", "Hiragino Kaku Gothic ProN", "Yu Gothic", Meiryo, "Noto Sans CJK JP", sans-serif` | 400 / 700 | 読み込まない                                                   |
| 記事の題と見出し | Zen Old Mincho。代替は本文の書体の列                                                                            | 600       | Fontsource の分割を self-host し、ビルドで使う字だけに作り直す |
| 等幅             | Noto Sans Mono                                                                                                  | 400 / 700 | Fontsource の分割を self-host する                             |
| 等幅の中の和文   | BIZ UDGothic                                                                                                    | 400 / 700 | Fontsource の分割を self-host する                             |

- 本文の書体の列は、計測に使った列である。どの書体も無い端末は、ブラウザの `sans-serif` で描く。
- 本文の書体の列は、プリミティブトークンの `--fd-primitive-font-family-sans` の 1 か所に置く。テーマ変数の `--font-sans` と `--font-heading` は、この値を参照する。
- 本文の欧文は、端末の和文の書体が持つ Latin で描く。欧文の Web フォントを足すと、本文の取得が戻るためである。
- 和の感じは、記事の題と見出しの明朝で残す。主の色は ADR-0024 に、挿絵は ADR-0026 にある。
  - ADR-0024: [トークンを、fukuemon.dev の値のプリミティブトークン、セマンティックトークン、テーマ変数の 3 つの層にし、生成りの地と旧サイトの差し色で、角丸と影を使わない版面にする](0024-tokens-of-fukuemon-dev.md)
  - ADR-0026: [トップの最初の訪問で水墨の門を描き、門をくぐった立体の庭にプロフィールを置く](0026-sumi-gate-and-garden-on-top.md)
- 和文の Web フォントに、可変の書体を使わない。和文の Web フォントは書体ごとに 1 つか 2 つのウェイトしか使わないので、ウェイトの軸の分の転送量を払う理由がない。
- Web フォントは Fontsource で self-host し、外部の CDN から読まない。同一オリジンから配れば、COEP の下でもサードパーティのヘッダの方針に左右されない。
- どの Web フォントも `font-display: swap` にし、`size-adjust` で差し替えのずれを抑える。和文の分割は preload しない。

## 承認の条件

- Windows と Android の端末で、本文が列のどの書体で描かれるかと、記事のページの見た目を確認する。確認の結果で、本文の書体の列の中身と順を直す。

## Verification

2 回目以降の訪問のトップを `pnpm run measure:top` で測った（Metal、mobile、各案 5 回）。  
対象は develop の 5825f0e に、案ごとの実験の変更を当てたものである。  
端末の書体の案は、Decision の本文の書体の列で測り、macOS の Hiragino Sans で描かれた。

| 案                       | Performance（中央値と範囲） | LCP    | FCP    | フォントのリクエスト | フォントの転送量 | CSS の転送量 |
| ------------------------ | --------------------------- | ------ | ------ | -------------------- | ---------------- | ------------ |
| 端末の書体               | 92（88〜92）                | 2.86 s | 1.50 s | 6                    | 34 KiB           | 112 KiB      |
| サブセット（1 ファイル） | 87（85〜88）                | 3.46 s | 1.51 s | 8                    | 173 KiB          | 112 KiB      |
| サブセット（分割のまま） | 82（80〜82）                | 4.21 s | 1.80 s | 34                   | 143 KiB          | 179 KiB      |
| 今の構成                 | 75（70〜92）                | 5.71 s | 1.80 s | 34                   | 386 KiB          | 179 KiB      |

- サブセットの 2 つの案は、サイトの 291 字だけのファイルで測った。
- 今の構成の 92 の 1 回は、庭の最初の 1 枚がページの最初の描画に入り、LCP が FCP と同じ 2.71 秒になった回である。
- devtools のスロットリングで 6 回ずつ測った。
  - 端末の書体の案は、Performance が 80〜82、LCP が 3.56〜3.61 秒、TBT が 240〜281 ms だった。
  - 今の構成は、4 回が Performance 79〜84、LCP 3.42〜3.86 秒、TBT 0 ms だった。2 回は load が 7.3〜7.4 秒まで延び、Performance 53 と 58、LCP 7.35〜7.46 秒だった。
  - 端末の書体の案に、load が延びる回は無かった。
- どの案も、LCP の 2.5 秒には届かなかった。
- 合否に使う測り方（GPU とスロットリング）は、まだ決めていない。
- 最初の訪問、記事のページ、Windows と Android の端末は測っていない。

| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| Noto Sans JP を、サイトで使う字だけのウェイトごとの 1 ファイルにする          | 字形がどの端末でも同じになる。Performance が 75 から 87 に上がった                                                                                                                                                                                                | 90 に届かない。記事が増えて字が増えると、ファイルが大きくなる。apps/playground と Storybook にも、作り直す処理が要る。訪問者が入力した、ファイルに無い字は別の書体で描かれる |

| 今の構成（Noto Sans JP の分割をそのまま配る）                                 | DADS と同じ書体で、字形がどの端末でも同じになる                                                                                                                                                                                                                   | Performance が 75、LCP が 5.71 秒で、要求に届かない                                                                                                                          |
| BIZ UD の一族でそろえる（本文 BIZ UDPGothic、見出し BIZ UDPMincho）           | 本文、見出し、等幅の字形がそろう                                                                                                                                                                                                                                  | 和の感じが弱い。本文の Web フォントの取得が残り、今の構成と同じ理由で要求に届かない見込みである（測っていない）                                                              |
| 本文も明朝（Zen Old Mincho）                                                  | 和の感じが最も強い                                                                                                                                                                                                                                                | 本文の字が多く、読み込む量が最も大きい。DADS がサンセリフを選んだ理由とも合わない                                                                                            |

## Consequences

### Positive

- 本文の Web フォントの取得がなくなり、描画を止める CSS が gzip で 179 KiB から 112 KiB に減る。トップの FCP は 1.80 秒から 1.50 秒になった。
- 代替の書体から差し替わるときのずれが、本文で起きない。
- 記事のページも、本文の Web フォントを取得しなくなる。記事のページの値は測っていない。

### Negative

- 本文の見た目が、端末の書体で変わる。Hiragino Sans、Yu Gothic、Meiryo、Noto Sans CJK JP のどれで描くかで、字の幅、行の折り返し、太さが違う。
- DADS の書体から、本文も外れる。DADS のコンポーネントの見た目は、端末の書体で描いた状態で確認する。
- 記事の題と見出しは、Zen Old Mincho が届くまで本文の書体の列で描き、届いた後に明朝へ差し替わる。
- LCP の 2.5 秒には、この決定だけでは届かない。残りは庭のバンドルの取得によると推測する。
- 描画を止める CSS には、見出しの明朝と等幅の `@font-face` が 384 件残る。
- 見た目の回帰テストのスクリーンショットの本文は、テストを流す環境に入っている書体で描かれる。
