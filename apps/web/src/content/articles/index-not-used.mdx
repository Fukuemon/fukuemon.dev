`CREATE INDEX` は通ったのに、`EXPLAIN` に `Index Scan` が出ないことがあります。
このときは、次の 3 つを順に確かめます。

## 1. 統計情報が古い

プランナは、テーブルの中身ではなく、`ANALYZE` が作った統計を見て計画を選びます。

最頻値の一覧が全行を覆う列では、統計に無い値は、何行あっても 1 行と見なされます。
1 行しか返らない見積もりなら、インデックスを使うコストは低く見えます。逆に、消えたはずの値がまだ多いと見積もられていれば、インデックスのコストは高く見えます。

統計がいつ作られ、その後にどれだけ変わったかを見ます。

```sql
select last_analyze, last_autoanalyze, n_mod_since_analyze, n_live_tup
from pg_stat_user_tables
where relname = 'events';
```

`n_mod_since_analyze` が `n_live_tup` に対して大きければ、統計は実際のデータから離れています。
`ANALYZE` を実行して、`EXPLAIN` を取り直します。

大量に入れた直後、パーティションを付け替えた直後、一括で削除した直後は、統計が古いままです。
autovacuum は、変更が閾値 (デフォルトで 10% + 50 行) に届くまで `ANALYZE` を実行しません。

統計が原因かどうかは、見積もりと実際の行数を並べると分かります。
`EXPLAIN ANALYZE` の同じ行に出る 2 つの `rows=` を比べてください。左が見積もり、右が実際の行数です。

これが原因なら `ANALYZE` で直ります。次の 2 つは `ANALYZE` では直りません。

## 2. 型が暗黙に変換されている

列の型と比較値の型が違うと、Postgres は片方を変換します。
**列の側が変換されると、その列のインデックスは使えません。**

インデックスは、列のもとの値の順に並んでいます。`f(列)` の結果の順には並んでいないので、インデックスで探せません。

実行パネルで確かめます。

```sql run
create table if not exists codes (
  code varchar(20) primary key,
  n int not null
);
insert into codes (code, n)
select lpad(g::text, 20, '0'), g from generate_series(1, 20000) g
on conflict (code) do nothing;
create index if not exists codes_n_idx on codes (n);
analyze codes;

explain
select * from codes where n = 42;
```

`codes_n_idx` が使われます。
比較値を文字列で書いても同じです。`where n = '42'` では、定数の側が `int` に変換されるだけで、列は変換されないからです。

列の側を変換すると、計画が変わります。

```sql run
explain
select * from codes where n::text = '42';
```

計画からインデックスが消えて、`Seq Scan` になります。
`n::text` は列に関数を掛けた形です。インデックスは `n` の順に並んでいて、`n::text` の順には並んでいません。

列の側のキャストでも、インデックスを使えるものがあります。

```sql run
explain
select * from codes where code::text = '00000000000000000042';
```

この計画では、インデックスが使われます。
`varchar` から `text` は内部表現が同じ (binary coercible) なので、Postgres は変換そのものを省くためです。

よく出る書き方と、インデックスを使えるかどうかは次のとおりです。

| 書き方                                  | 何が起きるか                                           |
| --------------------------------------- | ------------------------------------------------------ |
| `where n = '42'`                        | 定数の側が変換される。インデックスを使える             |
| `where n::text = '42'`                  | 列の側が変換される。インデックスを使えない             |
| `where code::text = '...'`              | 内部表現が同じなので変換されない。インデックスを使える |
| `where date(created_at) = '2026-01-01'` | 列の側に関数が掛かる。インデックスを使えない           |
| `where lower(name) = 'x'`               | 列の側に関数が掛かる。インデックスを使えない           |

インデックスを使えるかどうかは、キャストの見た目では決まりません。`EXPLAIN` で確かめてください。

下の 2 つをインデックスで探したいなら、式そのものにインデックスを作ります。

```sql
create index on users (lower(name));
create index on events (((created_at at time zone 'Asia/Tokyo')::date));
```

`created_at` が `timestamptz` のとき、`date(created_at)` の結果は `TimeZone` の設定によって変わります。
そのため `date(created_at)` は `IMMUTABLE` ではなく、そのままの式ではインデックスを作れません。
上の例のようにタイムゾーンを固定した式でインデックスを作り、クエリの条件も同じ式で書きます。

`date(created_at) = ...` は、範囲条件に書き換えると、`created_at` のインデックスを使えます。

```sql
where created_at >= '2026-01-01' and created_at < '2026-01-02'
```

書き換えられるなら、式インデックスより範囲条件を選んでください。インデックスが 1 本少なく済みます。

## 3. 選択率が高い

統計も型も問題ないのに、インデックスが使われないことがあります。
このときは、**プランナが正しく判断している**可能性を先に考えてください。

`Index Scan` は、インデックスを読んでから、テーブル本体のページを読みに行きます。
条件に合う行が多いと、結局ほとんどのページを読むことになります。それなら最初から順に読んだほうが安い、という判断です。

分かれ目は「何 % の行が条件を通るか」です。
この境目は環境で変わります。`random_page_cost` が小さいほど、`effective_cache_size` が大きいほど、インデックスは高い選択率まで使われます。

見分けるには `Buffers` を見ます。
`Bitmap Heap Scan` の `Heap Blocks` がテーブルの全ページ数と一致していたら、インデックスを読んだうえで全ページを読んでいます。読むページ数は、インデックスを使わない場合と変わりません。

境目を自分で動かして、計画が切り替わる点を探す手順は [RDBMS のクエリ実行を理解する](/labs/rdbms-query-execution) にあります。

## それでも使われないとき

3 つとも当てはまらなければ、次を確かめます。

| 症状                                        | 原因と対処                                         |
| ------------------------------------------- | -------------------------------------------------- |
| 複合インデックスの 2 列目だけで検索している | 先頭の列が条件に無いと使えない                     |
| `ORDER BY` とインデックスの並び順が違う     | `DESC` / `NULLS LAST` をインデックスの側に合わせる |
| `LIKE '%x'` で始めている                    | 前方一致でないと B-tree では探せない               |
| `COLLATE` がインデックスと違う              | `COLLATE` が違うインデックスは使われない           |
| 見積もりは合っているのに計画が悪い          | 値の偏り。`Rows Removed by Filter` を見る          |

最後の行の原因は、統計では直りません。
プランナは、条件に合う行がインデックスの並びに均等に散らばっていると仮定します。偏っていると、`LIMIT` の付いたクエリで見積もりが大きくずれます。
