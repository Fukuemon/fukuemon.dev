## 話題ごとの文書

デザインシステムの文書は、この文書と、次の 3 つの文書でできている。  
**画面とコンポーネントのコードを書く前に、この文書と 3 つの文書を全て読む。** この文書だけを読むと、トークンの使う場面と、コンポーネントの使い方と状態を知らないまま書くことになる。

| 文書                                             | 持つ規則                                                                           |
| ------------------------------------------------ | ---------------------------------------------------------------------------------- |
| [トークン](design/tokens.md)                     | セマンティックトークンの使う場面、テーマ、文字、レイアウト、区切り、重なり、動き   |
| [コンポーネントとパターン](design/components.md) | コンポーネントごとの使う場面、変種、状態、内容の制約、キーボードの操作と、パターン |
| [カタログ](design/catalog.md)                    | カタログのページ、題の決め方、カタログに載せてよいもの                             |

## 知りたいことごとの参照先

デザインシステムの文書には、使い方の規則だけを書き、値と振る舞いはコードを参照先にする。

| 知りたいこと                                                         | 参照先                                                                                                |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 色、文字、動きの時間と緩急の値                                       | `src/tokens/primitive.css`                                                                            |
| セマンティックトークンの名前と、プリミティブトークンのどの値を指すか | `src/tokens/semantic.css`（ライト）と `src/tokens/semantic-dark.css`（ダーク）                        |
| 画面のコードで書くユーティリティの名前                               | `src/tokens/theme.css`                                                                                |
| 静的なファイルが読むトークンの CSS                                   | `src/tokens/tokens.gen.css`（生成物）                                                                 |
| エンジンに渡すコードの色                                             | `src/tokens/code-theme.gen.json`（生成物）と、VS Code の形式のテーマを作る `src/tokens/code-theme.ts` |

## 画面を作るときの原則

<!-- 画面のコードで守る規則を、ID を付けた箇条書きにし、入れ子に確認の方法を書く。機械で判定できる原則はチェックの名前を、できない原則はレビューで見る問いと良い例と悪い例を書く。次の 10 個を出発点にし、プロダクトに合わせて直す。利用者が採ると決めたものだけを残し、残りは「決まっていない選択」へ移す。ID は、大文字の英語の語をハイフンでつなぎ、一度付けたら変えない -->

- `COLOR-TOKEN`: 色、文字、動きは、テーマ変数のユーティリティだけで書く。色の値とプリミティブトークンの名前を、画面のコードに直に書かない。
  - 確認: 色の値とプリミティブトークンの名前は、チェック（`pnpm run check:raw-values`）で見る。文字、動きの時間と遅れの値は、レビューで見る。アニメーションと緩急の任意値は、`MOTION-TOKEN` のチェックで見る。
- `STATE-NOT-COLOR-ONLY`: 状態を色だけで伝えない。エラーと注意には、文と印を色と一緒に出す。
  - 確認: レビューで、色を見分けられない人がエラーの場所と内容を読み取れるかを見る。
- `TEXT-MIN-SIZE`: 14px より小さい文字を使わない。本文と操作の文字は 16px にし、14px は補足だけに使う。
  - 確認: `pnpm run check:utilities`
- `PRIMARY-ACTION-ONE`: 主のボタンは、1 つの画面かダイアログに 1 つまでにする。
  - 確認: レビューで、画面の主の操作が 1 つに決まるかを見る。
- `FOCUS-ONE`: フォーカスの表示は 1 つのユーティリティだけを使い、コンポーネントごとに色や太さを変えない。
  - 確認: `pnpm run check:utilities`
- `TARGET-SIZE`: 押せる領域は 44×44 CSS px 以上にする。WCAG 2.2 の AA（2.5.8）の 24×24 より厳しい、AAA（2.5.5）の値を選んでいる。見た目を小さくするときは、見た目の外に押せる領域を広げる。
  - 確認: <コンポーネントのテストの名前>。カタログのアクセシビリティの自動チェックは、押せる領域の大きさを確認しない
- `SPACING-SCALE`: 余白は、トークンの文書の「レイアウト、区切り、重なり、動き」の表の余白の段のユーティリティだけで書く。任意値（`p-[13px]` のような書き方）を書かない。
  - 確認: `pnpm run check:utilities`
  - 入力欄と、その見出し、補足の文、誤りの文の間は、<フォーカスの表示が欄の外へ広がる幅より広い段>にする。狭いと、フォーカスの表示が近くの文字に重なる。
    - 確認: レビューで、欄と近くの文字の間が、その段以上かを見る。
- `LAYOUT-OVERFLOW`: レイアウトのブレークポイントの幅ごとに、ページの横方向のオーバーフローを出さない。長い文字とデータの多い状態でも出さない。
  - 確認: ページの全体の幅は、<描画した画面の確認のコマンド> で見る。内側の領域で切れた文字とボタンは、撮った画像をレビューで見る。
- `MOTION-TOKEN`: アニメーションと緩急は、トークンの文書の「レイアウト、区切り、重なり、動き」の表の動きのユーティリティだけで書く。任意値（`animate-[ping_1s_infinite]` のような書き方）を書かない。アニメーションの任意値はテーマ変数を通らないので、`MOTION-REDUCE` の止め方では止まらない。
  - 確認: `pnpm run check:utilities`
- `MOTION-REDUCE`: 利用者が OS で動きを減らす設定（`prefers-reduced-motion: reduce`）にしたときは、位置、大きさ、回転を動かすアニメーションと遷移、スクロールに合わせた動きを止める。残すのは、状態の変化を伝える短い透明度の変化と、機能に欠かせない動き（<残す動きと理由>）だけにする。WCAG 2.2 の AA に無い、AAA（2.3.3）の基準を選んでいる。止め方はテーマ変数のファイルの 1 か所に置き、画面のコードに設定ごとの条件を書かない。
  - 確認: レビューで、テーマ変数のファイルの止め方を見る。描画した画面で確認するなら、<動きを減らす設定で操作し、動いているアニメーションを調べるテストの名前>。

## 画面を作るときの手順

<!-- 画面とコンポーネントのコードを書く人が、この順に進め、受け入れ条件を満たしたら終える。スキル write-design-system は、このセクションを読んで作業する -->

### 順

1. 参照先の表、トークンの文書、コンポーネントの文書、カタログから、使うパターン、コンポーネント、トークンを探す。合うものがなければ、画面のコードで作らず、デザインシステムに足すかを尋ねる。
2. テーマ変数のユーティリティと、このデザインシステムのコンポーネントだけで書く。
3. 使ったコンポーネントの状態のうち、画面で起きるものを作る。
4. 下の「流すコマンド」を、表の順に流す。
5. 描画した画面を、トークンの文書のブレークポイントの幅ごとと、テーマごとに撮り、横方向のオーバーフローを確認する。撮った画像はレビューで見る。
6. チェックが通らなければ直し、手順 4 から流し直す。チェックの出力を見て自分で直すのは、2 回までにする。<!-- 回数を変えるときは、ここの数を直す -->
   - 2 回直しても通らないか、違反の数が減らないときは、直すのをやめて止まる。最後に全てのチェックが通ったコミットに、通らない変更を混ぜない。通らない変更は、コミットせずに差分として報告に添える。
   - 全てのチェックが通ったコミットが無いときは、作業を始めたときのコミットを代わりにし、そのときに既に通らなかった原則の ID を報告に書く。
7. 下の「報告の形」で報告する。止まったときは、最後に通ったコミットの SHA と、通らないまま残った原則の ID を書く。

### 流すコマンド

<!-- 実際に流すコマンドを、流す順に書く。前のコマンドが失敗したら、後のコマンドは流さずに「見ていない」と報告する。基準の画像と比べる確認（VRT）を選んだら、そのコマンドと、撮る環境と、基準の画像を撮り直すコマンドも書く -->

| コマンド                       | 見るもの                                                                 | 原則の ID                                                     |
| ------------------------------ | ------------------------------------------------------------------------ | ------------------------------------------------------------- |
| `pnpm run check:tokens`        | 2 つの生成物が、トークンと合っているか                                   |                                                               |
| `pnpm run check:contrast`      | セマンティックトークンの組のコントラスト比                               |                                                               |
| `pnpm run check:raw-values`    | 画面のコードの色の値とプリミティブトークンの名前                         | `COLOR-TOKEN`                                                 |
| `pnpm run check:utilities`     | 画面のコードの、原則に反するユーティリティ。規則の ID がこの文書にあるか | `TEXT-MIN-SIZE`、`FOCUS-ONE`、`SPACING-SCALE`、`MOTION-TOKEN` |
| <描画した画面の確認のコマンド> | 幅とテーマごとのページの横方向のオーバーフロー。撮った画像の置き場       | `LAYOUT-OVERFLOW`                                             |

### 受け入れ条件

- [ ] 「流すコマンド」が全て終了コード 0 で終わった
- [ ] 「確認の方法」がレビューの原則を、描画した画面で見た
- [ ] 幅とテーマごとに撮った画像を、レビューで見た
- [ ] 使ったコンポーネントの状態が、コンポーネントの文書のそのコンポーネントのセクションと合っている
- [ ] 報告に、5 つの状態のどれでもない原則がない
- [ ] 報告に、対象のコミット、コミットしていない変更の有無、デザインシステムの文書のバージョンがある

### 報告の形

<!-- 原則の ID ごとに、次の 5 つの状態のどれかで報告する。チェックの終了コードが 0 でも、レビューの原則の承認にはならない -->

| 状態           | 意味                                                                                 |
| -------------- | ------------------------------------------------------------------------------------ |
| 通った         | チェックが流れ、基準を満たした                                                       |
| 通らない       | 違反の証拠がある。場所と、出たチェックの出力を添える                                 |
| レビューで見る | 描画した画面かコードはあるが、判断はレビューの人がする                               |
| 見ていない     | 確認の規則、チェック、証拠のどれかが無い。前のコマンドの失敗で流していないものも含む |
| 対象外         | 作業の範囲から外れる。理由を添える                                                   |

<!-- 報告の冒頭に、どのコードと文書を見た結果かを書く。コミットしていない変更があると、コミットの SHA だけでは見たコードを特定できない -->

| 項目                               | 書くこと                                                                                                                                                                             |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 対象のコミット                     | チェックを流したときの `git rev-parse HEAD` の SHA                                                                                                                                   |
| コミットしていない変更             | なし、またはあり。ありのときは、変えたファイルの一覧（`git status --short` の出力）                                                                                                  |
| デザインシステムの文書のバージョン | この文書と 3 つの文書のどれかを最後に変えたコミットの SHA（`git log -1 --format=%H -- <この文書のパス> <3 つの文書のパス>`）。どれかにコミットしていない変更があれば、そのことも書く |

## アクセシビリティ

<!-- 基準と確認の方法を書く。確認の方法は、このプロダクトのテストとチェックの名前で書く -->

| 項目                         | 基準                                                                                                                                                                                | 確認の方法 |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| 文字のコントラスト           | 4.5:1 以上                                                                                                                                                                          |            |
| 文字でないもののコントラスト | 入力欄と押せる枠の境界、フォーカスの表示が 3:1 以上                                                                                                                                 |            |
| フォーカスの見え方           | 全ての操作できる要素で、フォーカスの表示を出す                                                                                                                                      |            |
| ターゲットの大きさ           | 44×44 CSS px 以上。AA の 2.5.8 の 24×24 より厳しい、このプロダクトの選択（AAA の 2.5.5）                                                                                            |            |
| キーボードの操作             | コンポーネントの文書のとおりに動く                                                                                                                                                  |            |
| 入力の誤りの伝え方           | 欄ごとの誤りの文は `aria-describedby` で欄に結び付け、`role="alert"` を付けない。送った後は最初の誤りの欄へフォーカスを移す。送れなかったときの文だけを `role="alert"` で読み上げる |            |
| 動きを減らす設定             | 設定が `reduce` のとき、位置、大きさ、回転を動かすアニメーションと遷移、スクロールに合わせた動きを止める。このプロダクトの選択（AAA の 2.3.3）                                      |            |
