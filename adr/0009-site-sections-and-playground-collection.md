# ADR-0009: サイトを about / blog / playground の 3 つのセクションに分け、playground を collection にする

## Status

承認

## Context

当初はトップページを成果物の一覧として作った。  
hero、最近の更新、種別ごとの節が並び、**「誰が書いているか」がどこにも無い**。

一方で、実行環境は Postgres だけに留まらない。  
TypeScript と Go は WASM で完結し、WebContainer は cross-origin isolation を要求する。  
**遊び場は増える前提である。**

現状の `/playground` は Postgres 専用の 1 ページを手書きしている。  
2 つ目を足すとページを複製することになり、記事とハンズオンで守っている「著者が触るのは Markdown 1 枚」が遊び場だけ破れる。

mermaid の配信量を測った。

| 方式                                 | 配信量         | ビルドの要件                    |
| ------------------------------------ | -------------- | ------------------------------- |
| ビルド時に SVG 化 (`rehype-mermaid`) | **0 バイト**   | `playwright` が peer dependency |
| クライアントで描画                   | **約 300 KiB** | 無し                            |

クライアント側の内訳は、エントリの 11 KiB に対し、必ず読み込む core chunk が 151 KiB + 147 KiB。  
図の種類ごとの chunk がさらに乗る (flowchart 37 KiB、sequence 30 KiB)。  
全 103 chunk で 0.95 MiB。

比べたときのバージョンは、`rehype-mermaid` が 3.0.0、`mermaid` が 11.17.2。  
`rehype-mermaid` は `mermaid-isomorphic` を経由し、その peer dependency が `playwright` 1 である。  
**CI に chromium の取得が要る。**  
`rehype-mermaid` の代わりには `@beoe/rehype-mermaid` と `astro-mermaid` がある。  
`mermaid` に代わるものは無く、事実上の標準である。  
出典: [rehype-mermaid](https://github.com/remcohaszing/rehype-mermaid)

## Decision

### サイトを 3 つのセクションに分ける

| セクション | URL           | 役割                                                 |
| ---------- | ------------- | ---------------------------------------------------- |
| about      | `/`           | 誰が書いているか。外部リンク。各セクションへのリンク |
| blog       | `/blog`       | 記事とハンズオン                                     |
| playground | `/playground` | 手順に縛られず動かす場所                             |

**about は独立したページを作らず、トップにまとめる。**  
別ページに切ると、トップが「他のセクションへのリンクだけのページ」になって 1 セクションぶん無駄になる。

**トップに最近の更新を残す。**  
自己紹介だけのトップは、更新が止まっているサイトと見分けが付かない。

### `/posts` を `/blog` に変える

読み手にとって「投稿」より「ブログ」のほうが指すものが明確である。

```text
/blog                記事 + ハンズオン
/blog/articles       記事だけ
/blog/labs           ハンズオンだけ
/articles/<path>     記事の本文
/labs/<path>         ハンズオンの本文
```

**本文の URL (`/articles` `/labs`) は変えない。**  
一覧の名前と本文の置き場は別の関心である。  
本文を `/blog/articles/<path>` にすると、一覧のパスと本文のパスが衝突する。  
ADR-0001: [Starlight を採らず、Astro 単体 + Expressive Code + Pagefind で組む](0001-starlight-as-docs-renderer.md)

### playground を content collection にする

`playgrounds` collection を足し、1 つの遊び場を 1 枚の Markdown で表す。  
URL は `/playground/<contentId>`、一覧は `/playground` にする。

**articles / labs / playgrounds の 3 つが同じ形になる。**  
遊び場を足す手順が、記事を足す手順と同じになる。

`/playground/*` には cross-origin isolation を予約済みである。  
ADR-0006: [手を動かす場所を 4 つに分け、cross-origin isolation を `/playground/*` に限定する](0006-interactive-content-levels.md)

**遊び場を増やすたびに URL とヘッダの判断をやり直さずに済む。**  
WASM で完結する TypeScript と Go は isolation を要求しないが、同じ棚に置いても害はない。

### mermaid はフェンスの `run` で 2 通りに分ける

````text
```mermaid          ビルド時に SVG 化する。配信 0 バイト
```mermaid run      クライアントの島。書き換えて即座に描き直す
````

**SQL とまったく同じ規則である。** 著者が覚えることは増えない。

記事の図に 300 KiB を配らない。  
図を 1 つ置いただけで、本文しか読まない人にも配ることになる。

playground は 300 KiB を払う場所である。  
PGlite の 5.28 MiB を払っているのと同じ判断で、**押されるまで落とさない**。

CI に chromium の取得が加わることは許容する。  
静的サイトのビルドは push ごとに 1 回なので、2 分程度の増加で済む。

### デザインは既存の決定に従う

セクションを増やしても、デザインの基準は [design-system](../packages/design-system/DesignDoc.md) のままにする。  
「角丸を使わず、影で奥行きを作らない」「紙に刷った版面の見えを保つ」を about と playground にも適用する。

動きは状態の変化を伝えるときだけに使う。  
**about だけを例外にする。** トップの表紙を兼ねるセクションで、名乗りと一覧が順に現れる動きを持つ。

例外にする理由は、about が読み手に**判断してもらう場所ではない**ためである。  
一覧や実行パネルの動きは、読む手を止めさせるとそのぶん判断が遅れる。  
about に判断は無い。

例外の範囲も、他のセクションと同じ規則の中に収める。

- 位置は動かさない。変えるのは濃度と罫の長さに限る。
- 配る JavaScript は 0 バイト。`@starting-style` と `animation-timeline: view()` で組む。
- `animation-timeline` は Chrome 115 以降でだけ有効になる。
  - 対応しない環境では規則ごと無視され、**最初から見えている**。
- `prefers-reduced-motion: reduce` では最初から見えている。

## Considered Options

### トップの構成

| 選択肢                                             | 強み                                                                                             | 弱み                                                                                                                                                |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** about をトップにまとめ、最近の更新を残す | 誰が書いているかと外部リンクをトップに置ける。他のセクションへのリンクだけのページを作らずに済む | —                                                                                                                                                   |
| トップを成果物の一覧のままにする                   | 実装を変えなくてよい。読み手が最短で本文へ届く                                                   | 書いている人が分からない。技術記事は誰が書いたかで読み方が変わる。外部リンク (X / GitHub) の置き場が無い                                            |
| `/about` を独立したページにする                    | トップを一覧に保ったまま自己紹介を持てる。分量が増えてもまとめずに済む                           | トップが他のセクションへのリンクだけのページになり、1 セクションぶん無駄になる。自己紹介は分量が増えない。増えないものに 1 ページを与える理由が無い |

### 遊び場の増やし方

| 選択肢                                                                      | 強み                                                                                 | 弱み                                                                                                                                                          |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **採用:** `playgrounds` collection にし、1 つの遊び場を Markdown 1 枚で表す | 遊び場を足す手順が、記事を足す手順と同じになる。URL とヘッダの判断をやり直さずに済む | collection と schema を足す必要がある                                                                                                                         |
| playground をページの手書きで増やす                                         | collection と schema を足さなくてよい。遊び場ごとに自由な画面を作れる                | 2 つ目からページの複製になる。presets の形も 1 つずつ違ってよいことになり、共通の見た目が崩れる。「著者が触るのは Markdown 1 枚」という規約が遊び場だけ破れる |

### mermaid の描画

| 選択肢                                                                      | 強み                                                                                                     | 弱み                                                                                                         |
| --------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| **採用:** フェンスの `run` の有無で、ビルド時描画とクライアント描画に分ける | 記事の図の配信は 0 バイト。mermaid の playground を SQL と同じ仕組みで足せる。著者が覚える規則が増えない | 描画が 2 系統になる。CI に chromium の取得が要る                                                             |
| mermaid をクライアント描画に一本化する                                      | ビルドに chromium が要らない。実装が 1 系統で済む                                                        | 図を 1 つ置いた記事が 300 KiB を配る。測ると core chunk だけで 298 KiB。本文しか読まない人にも配ることになる |
| mermaid をビルド時描画に一本化する                                          | 配信が常に 0 バイト                                                                                      | **mermaid の playground が作れない。** 書き換えて描き直すには、クライアントに mermaid が要る                 |

## Consequences

### Positive

- 遊び場を足す手順が、記事を足す手順と同じになる。
- 図を置いた記事の配信量が増えない。
- mermaid の playground を、SQL と同じ仕組みで足せる。
- URL の名前が読み手の語彙に近づく。

### Negative

- `/posts` から `/blog` への変更で、既存の URL が変わる。
  - 公開前なので被リンクは無いが、公開後なら redirect が要る。
- CI に chromium の取得が加わる。
- mermaid の描画が 2 系統になる。
  - **フェンスの `run` の有無という 1 つの規則で分かれるので、著者から見た複雑さは増えない。**
