# ADR-0031: サブドメインに分ける規則を決め、1 つのアプリを 1 つの Worker とホスト名に割り当てる

## Status

提案

## Context

fukuemon.dev のドメインの下に、サイトのほかに、複数のアプリを置く。  
どれを fukuemon.dev に置き、どれをサブドメインに分けるかを決める必要がある。

- 配信は Cloudflare Workers Static Assets で行う。custom domain は Terraform が、deploy は Wrangler が管理する。
  - ADR-0005: [Cloudflare Workers Static Assets を採用し、基盤を Terraform、deploy を Wrangler が管理する](0005-workers-terraform-wrangler-boundary.md)
- カタログは、`design.fukuemon.dev` に置いている。
  - ADR-0021: [packages/ui に Base と Case の React のコンポーネントを置き、packages/ui の Storybook をカタログにする](0021-ui-components-and-catalog.md)
- 訪問者のアカウントを持たないので、サイトが持つ訪問者の値は、訪問者のブラウザに保存した値だけである。
  - ADR-0008: [読者の identity を前提とする機能を作らず、バックエンドを持たない](0008-no-reader-identity.md)
- プレイグラウンドは、訪問者がブラウザの中で使うツールの集まりである。最初のツールは、コードと SQL の実行環境である。キャンバスとスライドのエディタを、後から足す。訪問者が作ったファイル、図、スライドは、訪問者のブラウザに保存する。
  - 出典: [PRD](../PRD.md#実行環境とプレイグラウンド)
- 実行環境の方式は、実行環境の要求の prototype で決める。候補の WebContainers は、cross-origin isolation（`COOP: same-origin` と `COEP: require-corp`）を求める。
  - 出典: [WebContainers: Configuring Headers](https://webcontainers.io/guides/configuring-headers)
- 訪問者のコードが、実行環境のページと同じ origin で動くかは、実行環境の方式で変わる。
- 実行環境の要求は、訪問者が作ったファイルを URL で共有することを、範囲の外に置いている。
- cross-origin isolation は、サイト全体に適用せず、`/playground/*` だけに適用すると決めている。
  - ADR-0006: [手を動かす場所を 4 つに分け、cross-origin isolation を `/playground/*` に限定する](0006-interactive-content-levels.md)
- `COEP: require-corp` のページでは、CORP を返さないクロスオリジンのリソースがブロックされる。
- isolation のヘッダは、文書のレスポンスごとに返す。同じ origin の中で、返す URL と返さない URL を分けられる。
- キャンバスの候補の draw.io の Embed Mode は、draw.io のエディタを、別の origin の iframe で読む。そのレスポンスは、COEP と CORP のヘッダを返さない（2026-11-13 に確認した）。
  - 出典: [draw.io: Embed mode](https://www.drawio.com/doc/faq/embed-mode)
- isolation が要る実行環境を、別の origin の iframe で記事に埋め込むときは、iframe の側がヘッダを返しても、親の記事のページがヘッダを返さなければ、iframe の中は isolation の状態にならない。実行環境の要求の prototype で確認した。
- サイトを作り直すあいだ、本番は切り替える前のサイトを配信し続ける。開発中のサイトを、実機と E2E で確認する URL が要る。

## Decision

### 1. サブドメインに分ける規則

次のどれかに当たるものを、サブドメインに分ける。当たらないものは、fukuemon.dev に置く。

1. 訪問者が書いたコードを動かす。origin を分けて、サイトが保存した値に届かないようにする。
2. サイトと違うレスポンスヘッダか、アクセスの認証が要る。
3. サイトと別に作って別にデプロイする、独立したアプリである。

1 つのアプリは、1 つの Worker と 1 つのホスト名に割り当てる。  
1 つの Worker に、パスで複数のアプリを配置しない。アプリごとに、デプロイのタイミングとヘッダを分けるためである。

### 2. 割り当て

| ホスト名                       | 置くもの                                               | 当たる規則 |
| ------------------------------ | ------------------------------------------------------ | ---------- |
| `fukuemon.dev`                 | トップ、記事、シリーズ、プレイグラウンドの一覧のページ | 無い       |
| プレイグラウンドのサブドメイン | プレイグラウンドの全てのツール                         | 1、2、3    |
| `design.fukuemon.dev`          | カタログ                                               | 3          |
| `docs.fukuemon.dev`            | ドキュメントサイト                                     | 2 と 3     |

- プレイグラウンドのサブドメインの名前は、実行環境の方式を決める ADR が決める。
- ゲームのような独立したアプリは、足すときに、規則 3 でサブドメインを 1 つ割り当てる。

### 3. プレイグラウンドのツールの配置先

- プレイグラウンドは、1 つのアプリとして扱う。全てのツールを、1 つのサブドメインの、1 つの Worker に置く。訪問者から見て 1 つの場所にし、ツールの間で、訪問者が保存した値を使えるようにするためである。
- ツールごとに、パスと文書を分ける。
- cross-origin isolation のヘッダは、isolation を求めるツールのパスにだけ返す。サブドメインの全体には返さない。別の origin の文書を iframe で読むツールを、同じサブドメインに置くためである。
- この Worker は、パスごとにヘッダを書き分ける。規則の「アプリごとにヘッダを分ける」の例外になる。
- どのパスにヘッダを返すかは、実行環境の方式を決める ADR が決める。

### 4. プレイグラウンドに保存した値

- プレイグラウンドのコードは、fukuemon.dev が保存した値に届かない。origin が違うためである。
- プレイグラウンドの中では、ツールの間で origin を分けない。訪問者が動かしたコードが、同じ origin に保存したファイル、図、スライドに届くことを受け入れる。理由は次の 3 つ。
  - 値は、訪問者の端末にだけある。訪問者のアカウントも、サーバーに置く値も無い。
  - 動くコードは、訪問者が書いたコードか、訪問者が自分の操作で動かしたコードである。
  - 作ったファイルを URL で共有しないので、他人が用意したコードが、訪問者の操作なしに動くことが無い。
- 次の 3 つを条件にする。
  - プレイグラウンドの origin に、シークレット（トークン、認証情報）を保存しない。
  - 訪問者の操作なしに、コードを動かさない。
  - URL での共有のように、他人が用意したコードを読み込む機能を足すときは、この決定を決め直す。

### 5. cross-origin isolation

fukuemon.dev のページには、cross-origin isolation のヘッダを書かない。  
サイト全体に適用すると、CORP を返さない外部のリソースが、全てのページでブロックされるためである。  
実行環境が isolation を求めるときに、どの URL に適用するかは、実行環境の方式を決める ADR が決める。

### 6. 切り替えまでのプレビュー

- 新しいサイトを、本番と別の名前の Worker（`fukuemon-dev-preview`）にデプロイする。custom domain を付けず、workers.dev の URL で開く。
- develop への push で check が通ったときにデプロイする。
- 誰でも開けるままにし、全てのレスポンスに `X-Robots-Tag: noindex` を返す。E2E と Lighthouse を、認証なしで実行するためである。
- 本番の Worker（`fukuemon-dev`）への deploy は、運用者が手動で実行したときだけ行う。
- 本番を新しいサイトに切り替えるときに、プレビューの Worker を消し、本番の Worker へ develop への push でデプロイする設定に替える。

## 承認の条件

次の 3 つを、実行環境の要求の prototype で確認する。

- isolation のヘッダを返すパスの文書と、返さないパスの文書が、同じ origin で両方動くこと。
- キャンバスの候補が、isolation のヘッダを返さないパスの文書で動くこと。
- 実行環境の方式が、訪問者のコードを、プレイグラウンドの文書と同じ origin で動かすか。同じ origin で動かす方式を採るときは、Decision 4 の受け入れを、その方式の ADR でもう一度判断する。

## Consequences

### Positive

- 新しいアプリを足すときに、配置先を規則で決められる。
- プレイグラウンドにツールを足すときに、Worker とホスト名が増えない。
- 開発中のサイトを、本番の Worker に触れずに、変わらない URL で確認できる。

### Negative

- Worker が、サイト、プレイグラウンド、カタログ、ドキュメントサイト、プレビューの 5 つになる。
- プレイグラウンドの Worker は、パスごとに違うヘッダを返す。ヘッダの設定を誤ると、isolation を求めるツールが起動しないか、iframe を読むツールが動かない。
- isolation を求めるツールと、別の origin の文書を iframe で読むツールは、同じ画面に並べられない。ツールを移るときは、文書を読み込み直す。
- 訪問者が、他人の書いたコードを貼って動かすと、そのコードが、同じ端末のプレイグラウンドに保存した図、スライド、ファイルを読むか、消すことがある。
- プレビューの Worker は custom domain を持たないので、Worker の名前を Terraform の変数と比べるチェックの対象の外になる。
- プレビューの URL を知っている人は、開発中のサイトを開ける。
